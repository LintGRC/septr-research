1 in 4 AI-built apps ships its .env file

AI-generated apps are supposed to be secure by default. The generators write the scaffolding, the developer writes the prompts. We scanned the full frame of Lovable-built apps on GitHub to find out what actually happens when you let a generator ship your code.

The durable figure presence, not exploitability

A file is either in the repository or it is not. This number doesn't depend on how the scanner works, what rules it applies, or what it misses — it's a binary fact. 242 of 881 Lovable apps commit their .env file to the public GitHub archive.

This is the durable figure. Lovable ships Vite + Supabase apps, so the typical .env holds a VITE_ URL and the anon key — public by design. But 1 in 4 of these files contains a service-role key, a database credential, or a real secret masked with a VITE_ prefix that publishes it to every visitor.

Most apps are safe and that matters too

But the headline tells only half the story. 448 of 881 apps came back with nothing at all — the median score is a perfect 100. Most Lovable apps are perfectly clean. The question is what happens to the ones that aren't.

7.3% score an F — and those 64 apps don't just leak placeholders. They ship real service-role keys, database credentials, and hardcoded AWS access keys. Septr's A-band share (84% vs ogbuilds' 64%) is higher because we role-verify Supabase keys from the JWT payload itself: 0/269 false positives on public-by-design anon keys.

What the scanner catches before verification

Before any human checks, the engine sees Supabase JWTs everywhere — because almost every Lovable app uses Supabase, and the anon key is meant to be public. The raw number looks alarming. The question is what it means.

The largest class — Supabase JWTs at 24.4% — is the ambiguous one. After role-verification from the JWT payload, all 269 anon-key findings verified as public-by-design. The class nobody would argue about — committed database connection strings — sits at a quiet 4.7%. This is why we verify before reporting a number.

Verification strips the noise the product story

This is the difference between a scanner that flags and a scanner that verdicts. Every finding in a seeded 50-repo subsample was handed an adversarial model with the surrounding code and told to argue it down. 89% of generic secrets were placeholders and docs examples. The role-verified rules lost nothing.

12.5% of what scanners report is false. The rules that verify from the value's own format (Supabase JWT role, Stripe key prefix) lost 0%. That's the gap Septr exists to fill: every other scanner stops at pattern matching; we stop at evidence.

What stays after verification is real the disaster tail

After verification, 64 apps still grade F. Not placeholders — real database credentials, real service-role keys, real hardcoded AWS access keys. These repos commit the .env and trip several credential classes at once. This is the population Septr is built for.

The F-grade tail is small — 7.3% — but it's where the real damage lives. A committed service_role key bypasses RLS and grants full database access. A committed database credential lets anyone connect. A committed AWS key burns quota. The rest of the apps are safe; these 64 are the reason a production scan exists.

A leaked key isn't equal blast radius, not prevalence

Not every committed secret is equally dangerous. A service-role key bypasses row-level security and grants full database access. An anon key is bounded by design — unless RLS is turned off. Blast radius tells you what would actually happen.

1 in 10 apps ships something that would grant data access if used. The anon key is the subtle case: it is safe because of RLS — but 27 of 210 anon-key apps (12.9%) turned RLS off. The bound that makes the key safe is the same bound you're supposed to keep.

They don't hide where you'd think the surprise

Every finding carries a file path. Where the secrets are tells you who could have seen them — and what an attacker would find first. The answer is counter-intuitive.

Docs are the leak surface, not the frontend. 33% of data-access credentials live in markdown — deployment checklists, connection analyses, setup guides — written down with instructions. The frontend bundle carries 5 data-access findings in 5 repos (0.6%): service-role JWTs shipped to every visitor. And config is where automation secrets live — n8n workflows with embedded service-role keys. The danger doesn't hide in the bundle.

The story holds across every population

The same engine, the same verification, different generators — different leak mechanics. v0 apps leak through hardcoded code (15.4% data-access tier), self-described AI-coded apps leak at 1.5% unfiltered (7.7% app-shaped), and Lovable's 27.5% is a Lovable property, not an AI-coding property.

The exposure tracks how much real app wiring exists — and the leak mechanics follow the generator. That is the argument for scanning the whole class of AI-built apps, not any single framework.

Methodology

Frame: GitHub code search lovable-tagger filename:package.json — the complete enumerable surface for Lovable apps on GitHub. 900 repos sampled in a fixed seeded order (seed 20260812); 881 downloaded (19 exceeded the 150 MB archive cap). GitHub's code search caps at 1,000 results per query, so the frame is the full surface, not a subsample.

Scan: Septr's rules engine over each repo's GitHub tarball, offline. Three rule families: existence checks (durable by construction), bundle checks (per text file, role-aware for Supabase JWTs), and duplication checks (content-hash families). Committed .env files get content-derived severity — one finding per live-secret line at that line's severity.

Verification: a seeded 50-repo subsample produced 361 findings, each adjudicated one at a time with the surrounding code (redacted), using the same model that builds Septr, under the ogbuilds rule: only high-confidence drops count. 45/361 dropped (12.5%). The verification subsample was selected deterministically and the task IDs are stable — nothing was selected after seeing the results.

Ethics: aggregates and anonymized rows only — no repo-to-credential mapping, no confirmed-live credential testing. Establishing that a key still works means using someone's credential against their account, which is not a thing this study will do.

Every proportion carries a 95% Wilson confidence interval in the aggregates file. A percentage from a sample without one invites the reader to treat it as exact.
